## 0. 结论先行

1. **项目整体可行，但必须限定范围。**“自动发现设备、展示信息、对能读的设备读电量、读不到时诚实解释”完全可以做；“任意 2.4GHz 无线外设都能读出电量”做不到，这是设备固件和厂商协议决定的，不是软件实现问题。
2. **真正能通用覆盖的只有两类**：① 蓝牙 BLE 设备（Windows 系统属性 / 标准 GATT 电量服务）；② 罗技的 2.4G 与蓝牙设备（HID++ 2.0 厂商协议）。其他品牌的 2.4G 接收器，绝大多数在系统里只是一个普通 HID 键盘/鼠标接口，**不暴露电量**。
3. **接收器本身没有电池。**USB 接收器由总线供电，能展示的是“接收器已连接/固件/配对数量”，不是“接收器电量”。原需求中“接收器自身状态”和“外设电量”必须分开表达。
4. **推荐技术栈：WPF + .NET 10 LTS + MVVM + SQLite。** 理由是本项目大量依赖 Win32/HID 互操作、托盘、图表和单文件发布，WPF 的成熟度与可控性最高；WinUI 3 的现代标题栏更好，但托盘、打包和互操作成本更高（详见 §4.1）。
5. **最大风险不是技术，而是预期落差。** 如果首版宣传成“所有无线外设都能看电量”，用户拿杂牌鼠标一试就会失望。产品必须把“支持矩阵”和“读不到的原因”做成第一等公民。
6. **需要你拍板 5 个 P0 事项**（技术栈、首版适配范围、交付节奏、托盘提醒方式、分发方式），见 §7。其余事项我给了默认值，你不反对我就按默认执行。

## 1. 我对软件目标的理解

### 1.1 一句话定义

**Vita Trace 是一个常驻 Windows 托盘的“外设状态与电量可信度面板”**：自动发现键盘、鼠标、接收器和蓝牙设备，尽可能读取真实电量，并把“数据从哪来、什么时候读的、可不可信、为什么读不到”一并告诉用户。

三个关键词：

- **发现（Discover）**：设备插入/拔出/重连都能及时反映，不依赖用户手动扫描。
- **读取（Read）**：按设备实际能力选择协议，能读则读，不能读则明确说明。
- **解释（Explain）**：这是产品与“系统设置里那个电量数字”的差异所在——读不到时给出原因和下一步，而不是空白、转圈或假数字。

### 1.2 核心价值

| 价值 | 具体表现 |
|---|---|
| 集中 | 一个窗口看完鼠标、键盘、接收器、蓝牙设备，不用逐个打开厂商软件 |
| 可信 | 每个百分比都有来源（系统属性/GATT/HID++）、时间戳和可信度标记 |
| 可解释 | “不支持读取”“读取失败”“设备已断开”“接收器已断开”是四种不同状态，不混为一谈 |
| 可追溯 | 本地历史曲线，能看出是缓慢耗电还是突然掉电 |
| 轻量 | 无驱动、无服务、默认不联网、普通用户权限即可运行 |

### 1.3 目标用户与场景

- **大学生**：宿舍桌面，一两百元的无线键鼠 + 蓝牙耳机/手柄，设备杂、品牌多，最需要“到底能不能读”的诚实反馈。
- **打工人**：工位 + 家里两套设备，罗技/微软/Keychron 较多，关心低电量提醒和开会前检查。
- **共同点**：不会为了看电量去装厂商全家桶；对“装了软件还是读不到”容忍度低；希望界面干净、别卡。

### 1.4 必须坚持的设计原则

1. **真实性 > 完整性 > 美观。** 没有数据就显示“—”，绝不生成随机数或固定值。
2. **能力探测优先于型号硬编码。** 先问设备“你支持什么”，再决定怎么读；型号表只用于命名和兜底。
3. **每个数字都有来源和时间。** UI 上必须能看到“系统属性 / GATT / HID++ / 标准 HID”和“最后更新”。
4. **失败可解释、可重试。** 错误信息要能指导用户（例如“请先在 Windows 设置中配对”），而不是只显示“读取失败”。
5. **最小权限。** 不要求管理员、不装驱动、不装服务、不写系统关键位置。
6. **UI 不阻塞、不闪烁、不造假。** 所有 IO 异步；刷新有节流；加载态用骨架屏，不用假百分比占位。

### 1.5 首版范围（建议）

**做：**

- USB/HID/蓝牙设备枚举、热插拔、设备信息展示
- 接收器识别（启发式 + 置信度）与“接收器 → 外设”映射（仅罗技可做）
- 蓝牙 BLE 电量（系统属性 + GATT 兜底）
- 罗技 HID++ 2.0 电量（2.4G + 蓝牙）
- 标准 HID Battery Strength 的机会性探测
- 设备卡片、电量圆环、历史曲线、状态与可信度
- 低电量提醒、托盘、开机启动、中英切换
- 本地历史、别名/备注、日志、诊断导出
- 绿色版 + 可选按用户安装包

**不做（首版）：**

- DPI/宏/灯光/按键映射等外设控制
- 固件升级、驱动安装、厂商软件替代
- 云同步、账号、手机端
- 雷蛇/雷柏/VGN 等品牌的私有协议逆向适配（预留插件接口）
- 电量预测/AI 估算（没有真实数据时不做“猜”）
- 游戏联动、RGB 同步

## 2. 需求中需要澄清或修正的地方

### 2.1 四个需要修正的表述

| 原表述 | 实际情况 | 建议改法 |
|---|---|---|
| “接收器自身电量” | USB 接收器由总线供电，**没有电池**，不存在电量百分比 | 展示“接收器连接状态、固件版本、配对设备数”；外设电量单独展示 |
| “实时更新” | 绝大多数外设只能**轮询**；只有部分 BLE 设备支持 notify 订阅 | 定义为“手动刷新 / 定时刷新 / 连接事件触发”，默认 60 秒，最小 15 秒 |
| “低电量时任务栏图标闪动” | 程序最小化到托盘后**没有任务栏按钮**，`FlashWindowEx` 无对象可闪 | 托盘气泡 + 托盘图标红色叠加 + 主窗口可见时任务栏闪烁；需你确认优先级（§7-Q4） |
| “支持所有无线外设” | 不同品牌/型号的固件是否暴露电量完全不同，没有统一标准 | 改为“支持矩阵 + 逐设备能力状态”，UI 明确写“不支持读取” |

## 3. 关键技术可行性调查

### 3.1 Windows 能提供什么

| 能力 | 主要 API / 机制 | 能拿到 | 主要限制 | 证据 |
|---|---|---|---|---|
| USB/HID 枚举 | SetupAPI（`SetupDiGetClassDevs`、`SetupDiEnumDeviceInterfaces`）、CfgMgr32 | 设备实例 ID、VID/PID、厂商/产品字符串、设备路径、父设备、容器 ID | 字符串可能为空或本地化；克隆设备共享 VID/PID | A |
| HID 能力解析 | `HidD_GetAttributes`、`HidD_GetProductString`、`HidP_GetCaps`、报告描述符 | 用法页/用法、报告长度、输入/输出/Feature 报告 | 需要逐设备解析；复合设备有多个集合 | A |
| 设备属性 | `SetupDiGetDeviceProperty` / `DEVPKEY_*` | 厂商、型号、容器 ID、总线类型、友好名称 | 属性因驱动/设备而异，可能缺失 | A |
| 热插拔 | `CM_Register_Notification`（`GUID_DEVINTERFACE_HID`）、`WM_DEVICECHANGE` | 插入/拔出/重连事件 | 事件可能重复/延迟，需要去抖与兜底轮询 | A |
| 蓝牙 BLE 电量（系统） | PnP 属性 `{104EA319-6EE2-4701-BD47-8DDBF425BBE5}` PID 2 | 百分比（部分设备还有充电状态） | 仅 BLE 较可靠；缓存可能滞后；经典蓝牙常无 | B |
| 蓝牙 GATT | `Windows.Devices.Bluetooth`、`GattCharacteristic` | 标准 Battery Service（0x180F / 0x2A19）读数/通知 | 需配对/连接；首次连接慢；部分设备要求绑定 | A |
| 罗技 HID++ | 厂商 HID Feature Report（报告 ID 0x10/0x11） | 电量、充电状态、电压、配对设备、WPID | 协议非 Windows 官方文档；固件差异；需逐设备能力探测 | B |
| 标准 HID 电量 | Usage Page 0x06 / Usage 0x20（Battery Strength） | 0–100 的百分比 | 实际实现的键鼠很少；报告布局各异 | A/B |
| 系统电池 | `Windows.Devices.Power.Battery`、`GetSystemPowerStatus` | 整机电池百分比 | **不包含外设**，不能误用 | A |
| 托盘/开机启动 | `Shell_NotifyIcon`、HKCU `Run` | 托盘图标/菜单、登录自启 | 托盘模式下无任务栏按钮；自启路径需随安装位置更新 | A |

### 3.2 接收器识别：能做，但只能“启发式 + 置信度”

Windows **没有**“这个 HID 设备是不是 2.4G 接收器”的官方标志。可行做法是组合信号打分：

| 信号 | 权重 | 说明 |
|---|---|---|
| VID/PID 命中已知接收器库 | 强 | 例如罗技 Unifying/Bolt/Lightspeed 的接收器 PID；需要自建小库并允许更新 |
| 存在厂商自定义 Usage Page（0xFF00 及以上） | 强 | 多数厂商接收器会暴露私有 HID 集合 |
| 同一物理设备下有多个 HID 顶层集合 | 中 | 一个接收器常同时暴露键盘 + 鼠标 + 厂商集合 |
| 产品字符串含 Receiver/Dongle/2.4G/无线接收器 | 中 | 可能为空、被本地化，或普通设备误命中 |
| 设备类型为 HID、但只暴露厂商集合 | 中 | 可能是接收器，也可能是游戏外设 |
| 无电池服务、无标准键鼠用法 | 弱 | 只能作为辅助排除 |

输出三档，UI 用词必须跟着变：

- **高置信**：`接收器`（VID/PID 命中 + 厂商集合）
- **中置信**：`疑似接收器`（多个信号但未命中库）
- **低置信/未知**：`HID 设备`（不猜）

热插拔实现建议：

1. 主通道：`CM_Register_Notification` 监听 HID 设备接口变化。
2. 去抖：300–800ms 合并同一设备的重复事件。
3. 兜底：每 5 秒轻量轮询一次（只比较设备实例 ID 集合），防止漏事件。
4. UI 线程只接收“变更摘要”，枚举与解析全部在后台线程，避免卡顿。
5. 所有句柄用 `SafeHandle` 包装，设备拔出时取消挂起 IO。

### 3.3 电量读取的六条通路

| 通路 | 覆盖对象 | 依赖 | 实时性 | 权限 | 结论 |
|---|---|---|---|---|---|
| 1. 蓝牙 PnP 属性 | BLE 键鼠/部分外设 | 系统蓝牙栈已连接 | 缓存，秒级~分钟级 | 普通用户 | **首选蓝牙通路** |
| 2. BLE GATT 直读 | BLE 设备 | 配对 + 连接 + 设备暴露 0x180F | 可读可订阅 | 普通用户 | 作为刷新/兜底 |
| 3. 罗技 HID++ 2.0 | 罗技 2.4G / 蓝牙 | 厂商 HID 集合 | 轮询，秒级 | 普通用户 | **首版重点适配** |
| 4. 标准 HID 电量 | 极少数 HID 设备 | 设备实现 Usage 0x06/0x20 | 轮询 | 普通用户 | 机会性探测 |
| 5. 其他厂商私有 | 雷蛇/雷柏/VGN 等 | 逆向或厂商 SDK | 不一 | 不一 | 首版不做 |
| 6. 系统电池 API | 整机电池 | 无 | — | — | **不适用** |

#### 3.3.1 蓝牙 PnP 属性（推荐首选）

Windows 蓝牙栈在 BLE 设备连接后，会把 GATT Battery Level 缓存成 PnP 设备属性。Windows 11“设置 → 蓝牙和设备”里显示的电量，基本就是这条通路。

读取方式（PowerShell 仅用于验证，产品内用 SetupAPI）：

```powershell
Get-PnpDevice |
  Where-Object { $_.InstanceId -like 'BTHLE\*' } |
  ForEach-Object {
    Get-PnpDeviceProperty -InstanceId $_.InstanceId `
      -KeyName '{104EA319-6EE2-4701-BD47-8DDBF425BBE5} 2'
  }
```

- **优点**：不用自己连 GATT，速度快、稳定、与系统显示一致；不需要管理员。
- **缺点**：仅 BLE 较可靠；经典蓝牙通常没有；缓存可能滞后；部分设备会长期卡在 100%。
- **产品策略**：先用它拿初值；如果发现“长时间不变且设备在放电”，标记为“可信度低”，再用 GATT 复核，而不是直接相信。

#### 3.3.2 BLE GATT 直读

标准 Bluetooth Battery Service：

- Service UUID：`0x180F`
- Characteristic UUID：`0x2A19`（Battery Level，0–100）
- 通过 `BluetoothLEDevice` → `GetGattServicesForUuidAsync` → `GetCharacteristicsForUuidAsync` → `ReadValueAsync` 或 `WriteClientCharacteristicConfigurationDescriptorAsync` 订阅通知。

- **优点**：值最新；支持通知的设备可以做到“变化即更新”。
- **缺点**：首次连接 1–5 秒；可能唤醒设备；部分设备要求先配对/绑定；并发连接数有限；连接失败需要退避。
- **产品策略**：默认不主动长连；在“手动刷新、详情页打开、PnP 值可疑”时按需连接，读完即释放。

#### 3.3.3 罗技 HID++ 2.0（首版重点）

罗技接收器会暴露一个厂商 HID 集合，通过 Feature Report 与设备通信。社区成熟实现（Solaar、LogiOps）已验证的核心事实：

- 报告 ID：`0x10`（短报告）、`0x11`（长报告）。
- 设备索引：`0xFF` 表示接收器本身；`1–6` 表示配对的设备。
- 先通过 Root Feature `0x0000` 的 `getFeature` 查询目标 Feature 的索引，再发具体命令。
- 电量相关 Feature：
  - `0x1000` Unified Battery：`getStatus`（function `0x01`）返回百分比与充电状态。
  - `0x1001` Battery Status：`getBatteryLevelStatus`（function `0x00`）返回百分比/状态，`getVoltage`（function `0x01`）返回电压。
- 接收器还能枚举已配对设备（WPID、设备索引），因此可以做“接收器 → 外设”的映射。

- **优点**：覆盖罗技大部分 Unifying/Bolt/Lightspeed 设备；不需要安装 Logi Options+ 或驱动；不需要管理员；能拿充电状态。
- **缺点**：协议不是 Windows 官方 API，属厂商协议 + 社区文档；不同代际/固件有差异；部分老设备是 HID++ 1.0；装有 G HUB/Options+ 时可能争用设备；需要自建 WPID→型号表。
- **许可注意**：Solaar 与 LogiOps 都是 **GPL-2.0**。可以阅读其协议说明、用公开事实做**独立实现**，但**不要直接复制代码或数据库**，否则可能把项目拖入 GPL 约束。首版建议自建小型映射表，并允许用户自定义名称。
- **产品策略**：能力探测（Feature 是否存在）→ 读一次 → 失败降级到“不支持/读取失败”，不假设“罗技就一定支持”。

#### 3.3.4 标准 HID Battery Strength（机会性）

HID 规范在 Generic Device Controls（Usage Page `0x06`）下定义了 Battery Strength（Usage `0x20`），取值 0–100。理论上任何 HID 设备都可以实现。

现实是：**实现的键鼠非常少**。Windows 不会把它聚合到统一界面，需自己解析报告描述符、找到对应字段、按报告 ID 读取。

- **产品策略**：作为“探测项”存在——如果设备恰好实现了，就多一个来源；不把它当作卖点，也不为它做型号适配。

#### 3.3.5 其他厂商私有协议（首版不做）

雷蛇 HyperSpeed、雷柏、VGN/ATK、达尔优等，通常需要：

- 逆向厂商 HID 协议，或
- 调用厂商 SDK / 依赖厂商软件，或
- 安装内核驱动。

问题：维护成本高、固件一变就失效、法律与稳定性风险高、无法覆盖全型号。首版不做，但架构上预留 `IBatteryProvider` 插件接口，后续可按品牌逐个加。

#### 3.3.6 系统电池 API（不要误用）

`Windows.Devices.Power.Battery` 和 `GetSystemPowerStatus` 返回的是**整机电池**（笔记本/平板），不包含任何外设。它不能用来推断鼠标电量。这一点必须在代码层明确隔离，避免后续误接。

### 3.4 接收器与外设的对应关系

| 品牌/类型 | 能否映射 | 依据 | 产品表达 |
|---|---|---|---|
| 罗技 Unifying/Bolt/Lightspeed | 能 | HID++ 可枚举配对设备（索引 + WPID） | “接收器 → 鼠标/键盘”，显示配对序号 |
| 罗技蓝牙 | 部分能 | 设备直连，无需接收器 | 直接显示设备 |
| 其他 2.4G | 基本不能 | USB 描述符只描述接收器本身，配对表在厂商固件里 | “接收器（已连接）”，外设“未关联/未知” |
| 蓝牙 | 不需要 | 设备与接收器无关 | 直接显示 |

**关键约束**：不要用“设备名里含 Mouse/Keyboard”这种字符串匹配去猜映射。系统里接收器的产品字符串往往是“USB Receiver”，不是真实外设名；猜错比不猜更伤信任。

### 3.5 权限、驱动与系统组件

| 操作 | 需要管理员？ | 需要驱动/服务？ | 说明 |
|---|---|---|---|
| 枚举 USB/HID、读设备属性 | 否 | 否 | 标准用户即可；个别设备可能拒绝打开，需捕获并提示 |
| 读 HID Feature Report（HID++/标准电量） | 否 | 否 | 用 `CreateFile` 打开设备路径；被厂商软件占用时可能失败 |
| BLE 连接与 GATT 读写 | 否 | 否 | 需要蓝牙开启、设备已配对；首次可能弹配对确认 |
| 托盘、开机启动 | 否 | 否 | 自启写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run` |
| 按用户安装 | 否 | 否 | 安装到 `%LOCALAPPDATA%`，不触发 UAC |
| 全局安装/服务/驱动 | 是 | 是 | **不在计划内** |

结论：**不需要管理员权限，不需要厂商驱动，不需要额外系统组件。** 这是本项目能保持“绿色、轻量”的基础。

| 品牌/类型 | 连接 | 电量可读性判断 | 主要依据 | 备注 |

| 罗技 BLE 键鼠 | 蓝牙 | 中–高 | 系统 PnP 属性 + 可能支持 HID++ | 取决于设备是否暴露 Battery Service |
| 雷蛇 HyperSpeed | 2.4G | 低 | 无公开标准协议，通常依赖 Synapse | 首版不支持 |
| 雷柏 Rapoo | 2.4G | 低–未知 | 多为私有协议 | 需实测，不能承诺 |
| VGN / ATK / 达尔优 | 2.4G | 低–未知 | 私有协议/厂商软件 | 首版不支持 |
| 微软蓝牙键鼠 | 蓝牙 | 中 | BLE Battery Service | 取决于具体型号 |
| Keychron | 蓝牙 | 中 | BLE Battery Service 较常见 | 2.4G 型号需另测 |

**为什么不能通用**：USB HID 规范只保证“键盘/鼠标能工作”，**不保证**厂商把电量放进标准报告；2.4G 接收器的配对信息留在厂商固件里，Windows 设备树看不到。是否可读，取决于厂商有没有实现、实现了哪种协议。

### 3.7 可行性分级

**A. 通用可实现（不做逐型号适配）**

- 设备枚举、热插拔、VID/PID/路径/容器 ID/父设备
- 接收器启发式识别与置信度
- 设备卡片、详情、状态机、历史、图表、托盘、自启、中英切换
- 蓝牙 PnP 电量（对暴露该属性的 BLE 设备）
- 标准 HID 电量探测（对实现了的设备）

**B. 条件可实现（依赖协议/型号/固件）**

- 罗技 HID++ 电量与配对映射（需逐代验证）
- BLE GATT 直读（需配对、连接、设备暴露服务）
- “接收器 → 外设”映射（仅罗技等可枚举配对的接收器）
- 定时刷新频率（受设备响应能力限制）

**C. 不可通用实现**

- 任意品牌 2.4G 外设的电量
- 非罗技接收器的配对设备识别
- 所有设备的“真实时”推送
- 没有电量传感器的设备（无论软件怎么做都没有数据）

**Go / No-Go 判断**：

- 若目标是“做一个诚实、好用、覆盖主流蓝牙与罗技设备的面板”——**Go**。
- 若目标是“任何 2.4G 鼠标插上都必须显示百分比”——**No-Go**，建议改目标或限定支持清单。

### 3.8 真机验证方法（第四阶段执行）

**需要的硬件（请尽量提供）：**

1. 罗技 Unifying 或 Bolt 接收器 + 对应鼠标/键盘（至少 1 套）
2. 罗技 Lightspeed 游戏鼠标（1 个，用于验证不同代际）
3. BLE 鼠标或键盘（1 个，最好支持标准 Battery Service）
4. 杂牌 2.4G 键鼠（1 套，用于验证“读不到”的表达）
5. 有线键鼠（1 个，用于验证“无需电量”）
6. 可选：经典蓝牙鼠标、蓝牙耳机
7. Win10 22H2 与 Win11 各一台（或虚拟机 + USB 直通）

**验证步骤：**

1. **基线对照**：同时打开厂商软件（Logi Options+/G HUB）和 Windows 设置，记录电量；与 Vita Trace 对比，误差应 ≤5%。
2. **重复读**：同一设备连续读 10 次（间隔 30 秒），值应稳定；允许 ±1% 的协议抖动。
3. **放电观察**：从满电用到 10%，每小时记录一次；曲线应单调下降，不应出现无充电状态下的突跳（>10%/分钟）。
4. **热插拔**：插拔 20 次、换 USB 口、经过 Hub、睡眠/唤醒；进程不崩溃、句柄不泄漏、设备状态最终一致。
5. **不支持路径**：杂牌 2.4G 必须显示“不支持读取”，而不是 0%/100%。
6. **断开区分**：关掉鼠标电源 vs 拔掉接收器，UI 必须显示不同状态。
7. **原始数据**：记录 HID++ 请求/响应十六进制帧（脱敏），便于回归与问题定位；用固定帧做单元测试。

**准确性判定：**

- 与厂商软件误差 ≤5% 且趋势一致 → 可信。
- 只能读到“100%/未知”且长期不变 → 标记低可信，不宣称准确。
- 读不到 → 明确“不支持/读取失败”，不进入历史曲线。

### 3.9 最可能遇到的五个硬件兼容性问题

1. **杂牌 2.4G 键鼠完全没有电量通道。** 接收器只暴露标准键盘/鼠标 HID，厂商把电量留在私有固件里；系统、驱动、任何通用软件都读不到。这是用户投诉率最高、也最容易被误解为“软件没做好”的情况。
2. **罗技老设备 / 不同固件代的 HID++ 差异。** 部分老设备是 HID++ 1.0，部分新固件字段长度或 Feature 版本不同；同一型号不同批次也可能不同。必须“逐设备探测 + 失败降级”，不能按品牌一刀切。
3. **蓝牙电量缓存不可靠。** Windows 的 PnP 属性可能滞后、长期卡在 100%，经典蓝牙则常常没有标准电量；设备休眠时读数可能不更新。需要 GATT 复核 + “可能过期”标记。
4. **同型号设备无法区分。** 两个同款鼠标/接收器 VID/PID 相同，可能都没有序列号；Container ID 在克隆设备上也可能重复。只能靠路径 + 用户别名，并在无法区分时明确提示，不能张冠李戴。
5. **设备被厂商软件占用 / 权限拒绝。** 装有 G HUB、Options+、雷云等软件时，HID 设备可能被独占打开；部分设备的安全策略会拒绝标准用户读写。需要捕获共享冲突、提示关闭厂商软件、退避重试，而不是崩溃或误报“不支持”。

补充：Windows 10 与 Windows 11 的蓝牙栈行为不完全一致（例如 PnP 属性可用性、配对流程），同一设备在两种系统上可能表现不同，必须双系统验证。

**职责边界：**

- `Core` 不引用 WPF，可在单元测试中独立运行。

- `App` 只做展示与交互，所有 IO 通过 `await` + `CancellationToken`，不阻塞 UI 线程。

### 4.4 核心数据模型与状态机

**设备（Device）关键字段：**

- `Id`：稳定指纹（容器 ID + VID/PID + 序列号/路径的哈希）
- `DisplayName` / `Alias` / `Notes`
- `Kind`：Receiver / Mouse / Keyboard / Headset / Other / Unknown
- `Transport`：UsbReceiver / BluetoothLe / BluetoothClassic / Wired
- `Vid` / `Pid` / `Manufacturer` / `Product` / `Path` / `ParentId` / `ContainerId`
- `ReceiverId`：关联的接收器（可空）
- `IsConnected` / `LastSeenAt`
- `Capability`：是否支持电量、来源列表、是否支持充电状态
- `Battery`：当前读数（可空）

**电量读数（BatteryReading）：**

- `Percent`（0–100，可空）
- `VoltageMv`（可空）
- `IsCharging`（可空：未知/充电/放电）
- `Source`：SystemPnp / BleGatt / LogitechHidpp / StandardHid
- `Confidence`：High / Medium / Low
- `UpdatedAt` / `RawPayload`（脱敏后的调试数据）

**状态机（UI 必须能区分）：**

| 状态 | 含义 | 进入条件 | UI 表达 |
|---|---|---|---|
| `Unknown` | 尚未探测 | 刚发现设备 | “检测中…” |
| `Unsupported` | 探测完成，无电量能力 | 所有 Provider 均返回不支持 | “不支持读取” |
| `Connecting` | 正在连接/唤醒 | BLE 连接、HID 打开中 | “正在读取…” |
| `Ok` | 有新鲜读数 | 读数在阈值内 | 圆环 + 百分比 + 来源 |
| `Stale` | 有旧读数但过期 | 超过 3 个刷新周期 | 百分比 + “数据可能过期” |
| `ReadFailed` | 有能力但本次失败 | 超时/拒绝访问/协议错误 | “读取失败” + 重试 |
| `Disconnected` | 设备或接收器断开 | 设备不在枚举结果 | “已断开”，保留最后值但不显示为当前 |
| `Wired` | 有线，无电池 | 总线类型为 USB 且有标准键鼠用法 | “有线 / 无需电量” |

关键规则：

- `Unsupported` 与 `ReadFailed` **绝不能混用**；前者是“设备没这个能力”，后者是“有能力但这次没读到”。
- `Disconnected` 时保留最后读数用于历史，但卡片必须显示“已断开”，不能拿旧值冒充当前值。
- `Stale` 仍显示数字，但加醒目标记；超过保留期则回到 `Unknown`。

### 4.5 刷新与采样策略

| 场景 | 策略 |
|---|---|
| 默认 | 每 60 秒刷新一次（可设 30s/1m/5m/15m/手动） |
| 最小间隔 | 15 秒；低于此值在设置中禁用并说明原因 |
| 多设备 | 错峰 + 抖动（±10%），避免同一秒集中请求 |
| 失败退避 | 30s → 1m → 2m → 5m → 15m；成功后重置 |
| 锁屏/睡眠 | 暂停；恢复后 5 秒内错峰刷新一次 |
| 手动刷新 | 立即执行，不受退避限制；单设备并发上限 2 |
| 写入历史 | 百分比变化或每 10 分钟心跳写一条；断连期间不插值 |
| UI 更新 | 仅当值/状态变化时通知；批量合并，避免每设备一次重绘 |

### 4.6 本地存储

| 项 | 建议 |
|---|---|
| 位置 | `%LOCALAPPDATA%\VitaTrace\`（数据库、日志、设置、导出） |
| 数据库 | `vitatrace.db`（SQLite，WAL 模式） |
| 表 | `devices`、`battery_samples`、`aliases`、`settings`、`schema_version` |
| 索引 | `battery_samples(device_id, sampled_at)` |
| 保留 | 默认 90 天；每日清理；每月 `VACUUM` |
| 迁移 | `schema_version` + 顺序迁移脚本；失败则备份并重建（不丢原文件） |
| 导出 | CSV（设备、时间、百分比、来源、可信度） |
| 隐私 | 全部本地；日志不记录完整序列号（只留后 4 位） |

**关键交互：**

- 标题栏：左侧应用名 + 小 Logo；右侧齿轮（设置）+ 最小化/最大化/关闭；拖动、双击最大化、Win11 Snap Layouts（`WM_NCHITTEST` 返回 `HTMAXBUTTON`）。
- 左侧列表：卡片式，含类型图标、别名/名称、状态点、迷你圆环/百分比；选中高亮；支持搜索与“全部/接收器/键鼠/蓝牙/有线”筛选。
- 右侧详情：大圆环（160px）+ 百分比；旁边历史曲线；下方来源、更新时间、可信度、充电状态；再下方设备信息与操作。
- 圆环：按电量分档配色（≥50 绿、20–49 琥珀、<20 红；充电时蓝色/闪电标记）；断连置灰；`Unsupported` 显示“—”而不是 0%。
- 曲线：默认 24 小时，可切 7 天/30 天；断连区间留空，不画直线插值；tooltip 显示时间、百分比、来源。
- 悬停动画：圆环轻微放大/发光（150–200ms），曲线显示十字线；动画只做透明度/缩放，避免布局抖动。
- 空状态：插画 + “未检测到设备” + “重新扫描” + 简短说明（“请插入接收器或开启蓝牙”）。
- 加载态：骨架屏；**绝不**用假百分比占位。
- 错误态：内联提示条 + 原因 + 重试按钮；例如“访问被拒绝：另一个程序正在使用该设备”。
- 多设备：列表虚拟化；详情独立滚动；窗口最小 900×600，默认 1100×720。
- 主题：浅色/深色/跟随系统；对比度满足 WCAG AA；支持 100%/150%/200% DPI。
- 键盘：Tab 顺序、Esc 返回、Ctrl+R 刷新；屏幕阅读器读取状态文本。

### 4.8 托盘、提醒、开机启动

**托盘菜单：**

- 打开 Vita Trace
- 立即刷新
- 暂停监控（30 分钟 / 1 小时 / 直到重启）
- 开机启动（勾选）
- 设置
- 退出

**低电量提醒：**

- 阈值默认 20%，可选 10%/15%/20%/25%；临界 10% 可再提醒一次。
- 迟滞：低于阈值触发一次；只有充到“阈值 + 5%”以上才重新武装，避免反复弹。
- 方式：托盘气泡 + 托盘图标红色叠加 + 主窗口可见时 `FlashWindowEx` 闪任务栏；可选提示音（默认关）。
- 不打扰：`Unsupported`/`Unknown`/`Disconnected` 不触发；全屏游戏/演示模式可自动静音（后续版本）。
- 托盘模式下没有任务栏按钮，`FlashWindowEx` 不适用——这是需要你确认的取舍（§7-Q4）。

**开机启动：**

- 写 `HKCU\Software\Microsoft\Windows\CurrentVersion\Run`，值为 `"<exe路径>" --tray`；不需要管理员。
- 便携版移动路径后，启动时自检并更新路径；卸载时删除该值。
- 单实例：命名 Mutex；第二次启动只唤醒已有窗口。

### 4.9 日志、隐私与安全

- 日志：Serilog 滚动文件，默认 Info；设备事件、Provider 尝试、错误堆栈；协议帧 Debug 级，默认关闭。
- 保留：14 天；单文件 10MB，最多 10 个；可“导出诊断包”（日志 + 设备清单 JSON，脱敏）。
- 隐私：默认不联网、无遥测、无账号；历史与别名只存本地；导出由用户主动触发。
- 安全：不请求管理员；不安装驱动/服务；不修改系统关键设置；HID 只发只读查询（Feature Index/Get Report），不发配置写入；所有长度/边界校验；所有 IO 设超时；异常不吞掉，写日志并呈现给用户。

## 附录 A：术语

| 术语 | 含义 |
|---|---|
| VID/PID | USB 厂商 ID / 产品 ID |
| HID | Human Interface Device，人机接口设备 |
| Usage Page / Usage | HID 用途分类与具体用途（如 0x06/0x20 = 电量） |
| HID++ | 罗技的厂商 HID 扩展协议，2.0 支持 Feature 查询 |
| WPID | Wireless Product ID，罗技无线产品标识 |
| GATT | 蓝牙低功耗的通用属性协议 |
| Battery Service | 蓝牙标准电量服务（0x180F / 0x2A19） |
| Container ID | Windows 用来把同一物理设备的多功能接口归组的标识 |
| PnP 属性 | Windows 设备属性，可通过 SetupAPI 读取 |
| Snap Layouts | Win11 最大化按钮悬停时的窗口布局菜单 |

## 附录 B：本阶段未验证事项（必须诚实列出）
